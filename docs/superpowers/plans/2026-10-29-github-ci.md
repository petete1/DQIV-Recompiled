# GitHub Actions CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On every push to `linux64` and on pull requests, GitHub builds the Linux 32-bit, Linux 64-bit and Windows 32-bit games without a ROM and runs the cheats tests. A pushed version tag (`1.9`, `1.8.1`, …) also packs the three release zips and attaches them to a draft release.

**Architecture:**
- One workflow, `.github/workflows/build.yml`, with four jobs: `linux64`, `linux32`, `windows` and `release`.
- The Linux jobs build inside an `ubuntu:22.04` container. Its glibc (2.35) is older than the one on the machine that built the 1.8 zips: those need **glibc 2.43** today, so they don't start on most distributions.
- Every job builds through the existing scripts (`build.sh`, `build.ps1`), the same way a player does.
- `release` runs only for tags. It downloads the three build artifacts and zips them into the release layout. It then creates a **draft** release, which the owner reviews and publishes by hand.

**Tech Stack:**
- GitHub Actions: hosted `ubuntu-latest` and `windows-2025` runners, and the `ubuntu:22.04` container.
- CMake ≥ 3.24 and Ninja (installed from pip in the container, since Ubuntu 22.04 ships CMake 3.22), and GCC 12.
- Visual Studio (preinstalled on the Windows runner), PowerShell, and the `gh` CLI (preinstalled on the runners).

**Spec:** The user's request "Investigate how to use github's CI", plus the earlier offer it answers: "A workflow could run whenever you push a tag like `1.9`: it would build the Linux zips and attach them to the release. A Windows runner on GitHub could do the Windows build, so we wouldn't need the Windows VM."

## Global Constraints

- **No game data in CI, ever.** No ROM, no `.obb`, no `assets/` (all three are in `.gitignore`). Every CI build is the ROM-less layout: the program plus `ROMandOBBfileHere/README.txt`.
- **Zip names and layout match the releases.** The names are `DragonQuestIV-linux32-<tag>.zip`, `DragonQuestIV-linux64-<tag>.zip` and `DragonQuestIV-win32-<tag>.zip`. Each holds `DragonQuestIV/DragonQuestIV` (or `DragonQuestIV/DragonQuestIV.exe`) and `DragonQuestIV/ROMandOBBfileHere/README.txt`, nothing else.
- **Debug tools stay built in.** This is the default, so no `nodebug` option is passed.
- **Release tags look like** `1.6`, `1.8`, `1.8.1`. The tag filter is `[0-9]*`.
- **The release is a draft**, titled with the tag. Nothing becomes public until the owner presses Publish.
- **The repository is** `petete1/DQIV-Recompiled`, and the default branch is `linux64`.
- **The Linux binaries must need at most GLIBC_2.35**, checked with `objdump -T`.
- **Third-party action pins** are the newest major version of `actions/checkout`, `actions/upload-artifact` and `actions/download-artifact`. Look them up when implementing: `gh api repos/actions/checkout/releases/latest -q .tag_name`, and the same for the other two.

## Review Focus

1. **i386 `-dev` packages that can't be installed** on Ubuntu 22.04, which would fail the `linux32` job. Expected: the job lists exactly which package failed. Its install step uses `apt-get install --no-install-recommends` with an explicit list, so a missing name fails loudly (Task 1, Step 4).
2. **SDL quietly missing Wayland or PulseAudio** because a header package is absent. A missing library "only leaves its feature out" (README), so the build still goes green. Expected: CI fails instead. Task 1, Step 3 greps `SDL_build_config.h` for the five drivers.
3. **A tag pushed twice, or a release that already exists.** Expected: the `release` job fails with gh's "already exists" message and doesn't overwrite anything (Task 3, Step 4).
4. **`build.ps1` waiting on `Read-Host`** on the runner, which would hang until the 6-hour timeout. Expected: it never prompts in CI. `Test-StartedFromExplorer` must return false there, and the job sets `timeout-minutes: 60` (Task 2, Step 4).
5. **`build.sh` picking up stale `assets`.** CI never has them, but a self-hosted runner could. Expected: the jobs start from a clean checkout (the default `actions/checkout` behaviour), and Task 1, Step 3 checks the zip is under 50 MB (the ROM-less program is about 11 MB; one with packed data is about 260 MB).

### Task 1: Linux builds and tests on every push

**Files:**
- Create: `.github/workflows/build.yml` (jobs `linux64` and `linux32`)
- Create: `.github/ci/linux-deps.sh`: installs the build dependencies. It takes one argument, `64` or `32`.
- Create: `.github/ci/check-linux.sh`: checks a built `dist/` folder. Its arguments are the expected ELF class (`64` or `32`) and the maximum glibc version (`2.35`).

**Interfaces:**
- Produces: artifacts named `linux64` and `linux32`. Each holds the folder `DragonQuestIV/` in the release layout, built by copying `dist/DragonQuestIV` and `dist/ROMandOBBfileHere` into it, as the earlier release builds did. Task 3 consumes them.

- [ ] **Step 1: Write `.github/ci/check-linux.sh <64|32> <max-glibc>`**

  It exits non-zero, printing why, unless all of these hold:
  - `file dist/DragonQuestIV` says `ELF 64-bit` or `ELF 32-bit`, matching the first argument.
  - The highest `GLIBC_x.y` in `objdump -T dist/DragonQuestIV`, compared with `sort -V`, is no higher than the second argument.
  - `dist/ROMandOBBfileHere/README.txt` exists.
  - `dist/DragonQuestIV` is under 50 MB.
  - `build*/_deps/sdl3-build/include-config-*/build_config/SDL_build_config.h` defines all of `SDL_VIDEO_DRIVER_X11 1`, `SDL_VIDEO_DRIVER_WAYLAND 1`, `SDL_AUDIO_DRIVER_PULSEAUDIO 1`, `SDL_AUDIO_DRIVER_ALSA 1` and `HAVE_LIBUDEV_H 1`.

- [ ] **Step 2: Run it locally against this machine's 64-bit build to see it fail**

  Run: `D=$(mktemp -d -p ~/.cache); git worktree add --detach $D/wt HEAD && cp -r .github $D/wt/ && (cd $D/wt && ./build.sh 64 && .github/ci/check-linux.sh 64 2.35)`.
  Expected: FAIL with a message naming `GLIBC_2.43` (this machine's glibc). That shows the glibc check works. All the other checks pass.
  Afterwards, run `git worktree remove --force $D/wt; rm -rf $D`.

- [ ] **Step 3: Write `.github/ci/linux-deps.sh <64|32>` and the two Linux jobs in `build.yml`**

  `linux-deps.sh`, run as root in `ubuntu:22.04`:
  - Common: `apt-get update`; install `ca-certificates curl git file binutils zip python3-pip gcc-12 g++-12 pkg-config libwayland-bin wayland-protocols`; `pip3 install "cmake>=3.24,<4" ninja`; `update-alternatives` (or export `CC=gcc-12 CXX=g++-12`) so that `c++` is g++ 12.
  - For `64`: install `libx11-dev libxext-dev libxrandr-dev libxcursor-dev libxi-dev libxfixes-dev libxss-dev libxtst-dev libwayland-dev libxkbcommon-dev libdecor-0-dev libegl-dev libgl-dev libpulse-dev libasound2-dev libudev-dev libdbus-1-dev`.
  - For `32`: run `dpkg --add-architecture i386 && apt-get update`, then install `g++-12-multilib` plus the same `-dev` list, each with the `:i386` suffix.

  `build.yml`:
  - Triggers: `push` on branches `[linux64]` and tags `['[0-9]*']`; `pull_request`; `workflow_dispatch`.
  - Permissions at the top: `contents: read`.
  - Both jobs use `runs-on: ubuntu-latest`, `container: ubuntu:22.04` and `timeout-minutes: 60`.
  - Their steps:
    1. checkout;
    2. `.github/ci/linux-deps.sh 64` (or `32`);
    3. `./build.sh 64` (or `./build.sh`);
    4. `.github/ci/check-linux.sh 64 2.35` (or `32 2.35`);
    5. the `linux64` job only: `python3 tests/cheats/run_host_tests.py`;
    6. stage `out/DragonQuestIV/` and upload it as artifact `linux64` (or `linux32`), with `retention-days: 14`.

- [ ] **Step 4: Push to a branch and watch it pass**

  Run: `git checkout -b ci && git add .github && git commit -m "CI: Linux builds and tests on GitHub" && git push fork ci`, then `gh run watch -R petete1/DQIV-Recompiled $(gh run list -R petete1/DQIV-Recompiled -b ci -L1 --json databaseId -q '.[0].databaseId')`.
  Expected: both jobs are green. The `linux64` log shows the cheats tests passing (242 checks), and both logs end with the check script's OK line.
  If an `:i386` package can't be installed, take the failing name from the log, replace or drop it, and note the dropped feature in the commit message.

- [ ] **Step 5: Download the linux64 artifact and run it here**

  Run: `gh run download <id> -n linux64 -D ~/.cache/dq4-ci`. Copy the ROM and `.obb` into `~/.cache/dq4-ci/DragonQuestIV/ROMandOBBfileHere/`, then start `~/.cache/dq4-ci/DragonQuestIV/DragonQuestIV`.
  Expected: the title screen appears, with the HD sound. Afterwards, `rm -rf ~/.cache/dq4-ci`.

- [ ] **Step 6: Commit** any fixes from Step 4 on the `ci` branch.

### Task 2: Windows build on the runner

**Files:**
- Modify: `build.ps1:84-118`. Without a ROM (and no `assets`), it builds the ROM-less layout instead of failing, as `build.sh` does.
- Modify: `.github/workflows/build.yml` (adds the `windows` job).

**Interfaces:**
- Consumes: the `build.yml` from Task 1.
- Produces: artifact `win32`, holding `DragonQuestIV/DragonQuestIV.exe` and `DragonQuestIV/ROMandOBBfileHere/README.txt`. Task 3 consumes it.

- [ ] **Step 1: Change `build.ps1` to match `build.sh`'s ROM-less path**
  - With no ROM: `Write-Warning "No ROM in $inbox: the game is compiled without its data."` instead of `throw`.
  - Packing: if `assets\data\SOUND\sound_data.sdat` exists, run `& $pack build32\Release\DragonQuestIV.exe assets addons dist\DragonQuestIV.exe` (unchanged).
  - Otherwise, run `& $pack build32\Release\DragonQuestIV.exe addons dist\DragonQuestIV.exe`, create `dist\ROMandOBBfileHere`, and copy `ROMandOBBfileHere\README.txt` into it.
  - Then print `Created dist\DragonQuestIV.exe without the game's data: it reads the ROM and .obb put in dist\ROMandOBBfileHere.`
  - Update the header comment (lines 1–8) to say so, as `build.sh`'s does.

- [ ] **Step 2: Add the `windows` job**
  - `runs-on: windows-2025`, `timeout-minutes: 60`.
  - Steps:
    1. checkout;
    2. `powershell -ExecutionPolicy Bypass -File .\build.ps1`, then fail the step unless `dist\DragonQuestIV.exe` exists. `build.ps1` catches its own errors and doesn't set an exit code, so check for the file explicitly.
    3. Stage `out\DragonQuestIV\` and upload it as artifact `win32`, with `retention-days: 14`.

- [ ] **Step 3: Push and watch**

  Run: `git push fork ci` and `gh run watch …` (as in Task 1, Step 4).
  Expected: the `windows` job is green in under 30 minutes, and its log shows `Created dist\DragonQuestIV.exe without the game's data`.

- [ ] **Step 4: Confirm it never prompts**

  Check the `windows` log: it has no `Press Enter to close` line, and the step ended on its own.
  Expected: true. If the job instead sat until the timeout, make `Test-StartedFromExplorer` return false when `$env:CI` is set.

- [ ] **Step 5: Compare against the 1.8 Windows zip**

  Run: `gh run download <id> -n win32 -D ~/.cache/dq4-ci && unzip -l DragonQuestIV-win32-1.8.zip`.
  Expected: the same two files. The size of `DragonQuestIV.exe` is within a few hundred KB of 1.8's 11,890,008 bytes.

- [ ] **Step 6: Commit**

  ```bash
  git add build.ps1 .github/workflows/build.yml
  git commit -m "CI: Windows build; build.ps1 builds without a ROM like build.sh"
  ```

### Task 3: Draft release on a version tag, and docs

**Files:**
- Modify: `.github/workflows/build.yml` (adds the `release` job)
- Modify: `README.md`. Adds a short "Automatic builds" paragraph after the Linux build section: every push builds the three versions (see the Actions tab), and a tag makes a draft release.
- Modify: memory `dqiv-linux-port-repo.md`. Records the new release procedure: push a tag, wait for the run, check the draft, publish.

**Interfaces:**
- Consumes: the `linux32`, `linux64` and `win32` artifacts (Tasks 1 and 2).
- Produces: a draft release named after the tag, with the three zips attached.

- [ ] **Step 1: Add the `release` job**
  - `if: startsWith(github.ref, 'refs/tags/')`, `needs: [linux32, linux64, windows]`, `runs-on: ubuntu-latest`, `permissions: contents: write`.
  - Steps:
    1. Download all three artifacts.
    2. For each of `linux32`, `linux64` and `win32`, run `(cd <artifact dir> && zip -qr -X ../DragonQuestIV-<name>-${GITHUB_REF_NAME}.zip DragonQuestIV)`. Restore the Linux executable bit first (`chmod +x`), because artifacts drop it.
    3. Run `gh release create "$GITHUB_REF_NAME" --draft --title "$GITHUB_REF_NAME" --generate-notes -R "$GITHUB_REPOSITORY" DragonQuestIV-*.zip`, with `GH_TOKEN: ${{ github.token }}`.

- [ ] **Step 2: Try it with a test tag**

  Run: `git tag 0.0.1-ci ci && git push fork 0.0.1-ci`, then `gh run watch …`.
  Expected: all four jobs are green, and `gh release view 0.0.1-ci -R petete1/DQIV-Recompiled --json isDraft,assets -q '.isDraft, (.assets[].name)'` prints `true` and the three zip names.

- [ ] **Step 3: Check the zips**

  Run: `gh release download 0.0.1-ci -R petete1/DQIV-Recompiled -D ~/.cache/dq4-ci`, then `unzip -l` each zip, and `unzip -Z` the Linux ones to see the file modes.
  Expected:
  - Each zip has exactly the two files of its layout under `DragonQuestIV/`.
  - The Linux executables show mode `-rwx`.
  - The linux32 executable starts here, with the ROM copied into its folder.

- [ ] **Step 4: Check that a second release isn't overwritten**

  Re-run the job: `gh run rerun <id> --job <release job id>`.
  Expected: it fails with `a release with the same tag name already exists`, and the draft's assets are unchanged.

- [ ] **Step 5: Clean up the test tag**

  Run: `gh release delete 0.0.1-ci -R petete1/DQIV-Recompiled --yes --cleanup-tag && git tag -d 0.0.1-ci && rm -rf ~/.cache/dq4-ci`.
  Expected: `gh release list` no longer shows it.

- [ ] **Step 6: Docs, then merge**
  - Write the README paragraph and the memory update.
  - Commit `"CI: draft release from a version tag"`.
  - Ask the owner before merging `ci` into `linux64` and pushing, since pushing is theirs to approve. After merging, delete the `ci` branch on the fork.
